# PostgreSQL financial HA profile

This opt-in Patroni bootstrap profile requires three quorum-store voters across independent failure domains, separate PostgreSQL hosts, an operable watchdog on every eligible leader, per-node certificates, and a working pgBackRest repository. Supply the watchdog device, Patroni scope and node name, PostgreSQL data directory, REST and PostgreSQL listen and advertised addresses, etcd3 endpoints, CA/cert/key paths and PostgreSQL authentication from the deployment secret manager. Configure replication, rewind and superuser clients to use verify-full with matching certificates. Limit network access to the participating nodes. Validate the effective configuration using the installed Patroni version before bootstrap. Patroni bootstrap DCS settings apply to a new cluster. Change an existing cluster through its DCS configuration and review the effective state.

Use the leader-only Patroni primary health endpoint for the writer proxy. Keep client pools behind that proxy. A read replica serves reporting only. Reserve server connections for migrations, reconciliation, replication and break-glass access before dividing the remaining database budget across PgBouncer pools. Use distinct database roles and pool quotas. Route Flyway over a direct TLS connection using SPRING_FLYWAY_URL, SPRING_FLYWAY_USER and SPRING_FLYWAY_PASSWORD. Use verify-full and a trusted CA on both pooler legs. For transaction pooling, set ELEPAY_DB_PREPARE_THRESHOLD=0 unless protocol-level prepared statement tracking has been enabled and verified on the installed PgBouncer. Rotate application credentials by provisioning the successor role, rolling pool credentials, draining old connections and then revoking the retired role.

The intended RPO is zero acknowledged commits for loss of one primary when its acknowledged synchronous standby survives, remains eligible, and the old primary is fenced. Loss of the last synchronous standby deliberately stalls commits. Monitor synchronous waiters, replication state and retained WAL. An ambiguous client outcome requires lookup by the original financial reference. Keep the old primary fenced during promotion. Rewind or rebuild it as a standby before rejoining. Measure client-visible recovery including leader election, proxy routing and pool reconnection before publishing an RTO.

Provide a pgBackRest configuration with encrypted offsite storage, TLS transport, versioned retention and a separately backed-up encryption key. Initialize the stanza, run check, take a full backup, and schedule subsequent backups. Restore to an isolated PostgreSQL host and select a recovery target before opening traffic. Compare journal counts, zero-sum totals, reconstructed balances, committed outbox IDs and idempotency results. Record restored WAL position, oldest recoverable timestamp, measured duration and discrepancies. Promotion and physical-copy recovery exercises alone do not establish point-in-time recoverability.
